# Tasks: Android App

**Input**: Design documents from `/specs/007-android-app/`
**Prerequisites**: plan.md, spec.md (US1-US6, FR-001..FR-061, SC-001..SC-012), research.md (R1-R18), data-model.md, contracts/ (ffi-api.md, android-policy.md, verify.md, shared-runtime-extraction.md), quickstart.md (D1-D25)
**Tests**: MANDATORY (Constitution III, TDD). Every implementation task is preceded by a test task that MUST be run and seen to FAIL (red) before the implementation task starts; refactor with tests green. A test task and its implementation task never run in parallel. Policy checks (`android/policy/check_*.py`) are preceded by negative unit tests and by the mutation harness; no Android file is written before its checker exists. Exception (plan.md Complexity Tracking, pending maintainer approval): Kotlin and Gradle behaviour has no red-first unit test because nothing can compile or run it on the host; it is gated by red-first policy checks, by the Rust tests of every decision the Kotlin shell only executes, and by device checks D1-D25.
**Organization**: Phase 2 is the host-extraction refactor (`crates/host-runtime`) and comes FIRST; `passwsyncd` tests stay byte-identical and green after every step (GATE-X). Phases 3-4 build the boundary crate shell and the policy gate. User stories follow in dependency order: US3 (P1) first because it creates the policy-clean Android skeleton every screen needs, then US1 (P1), US2 (P1), US4 (P2), US5 (P2), US6 (P3). Spec numbering is kept for labels.
**Security rules for every task**: no master password, wallet key, derived key or credential password in any log, error, file, sealed blob or Kotlin `String`; secrets cross the boundary only as wipeable byte vectors; the only `unsafe` is `crates/passwsync-ffi/src/memprotect.rs`; no change to the wallet format or the 003-005 protocols; no edit under `crates/passwsyncd/tests/**` (X1); no network access during verification; no Android SDK/NDK is available (see flags).

## Format: `- [ ] T### [P?] [Story?] Description with file path`

- **[P]**: different file, no dependency on an incomplete task
- Paths are relative to the repo root. Test tasks write the test only (red); the next numbered task makes it green.
- **(MANUAL)** = needs a real Android device or emulator and the SDK; cannot run in this environment. Stays unchecked until a person runs it and records the result in `specs/007-android-app/quickstart.md` ("Not run here" until then, with the automated equivalents named).
- **(ENV-BLOCKED)** = depends on a tool or resource absent from the dev host. Measured 2026-10-28: `cargo-deny` 0.20.2 and `cargo-audit` 0.22.2 are installed in `~/.cargo/bin` (absent from the PATH of some shells, so checks must use that path; verify.sh prepends it), the advisory DB is at `~/.cargo/advisory-db`, and the UniFFI 0.32.2 cache is complete. Still absent: `ktlint`, `gradle`, `adb`, Android SDK, NDK, Android Rust targets (present: `xmllint`, `python3`, `nm`). Such a check is written and unit-tested against stubs, reports `MISSING`/`SKIPPED` (never PASS) and completes only when the tool exists. Gradle/APK build and NDK build tasks (T-build items) are all MANUAL or ENV-BLOCKED.
- Kotlin and Gradle files cannot be compiled here: they are gated only by `android/verify.sh` static checks; their compile and run are D1/D-series device checks.

## Dependencies and execution order

- Phase 1 -> Phase 2 (strictly stepwise: steps 1..6, GATE-X after each) -> Phase 3 (`host-runtime` must exist) -> Phase 4 (independent of Phase 3 except T065+; can proceed in parallel with Phase 3 after Phase 2) -> user stories.
- Phase 5 (US3) needs Phase 4 (checkers) and creates the skeleton used by Phases 6-10 Kotlin tasks. Rust test tasks of US1..US6 need only Phase 3.
- Order of stories: US3 -> US1 -> US2 -> US4 -> US5 -> US6. US2 needs US1 (`start`, wallets); US4 needs US1 (lifecycle, identity); US5 needs US4 (peers) and T026; US6 needs US4 and US5 (pins, sync stores).
- `android/policy/mutations.py` and `android/policy/tests/api_inventory`-style files are edited by many tasks: those edits are sequential, never parallel. `crates/passwsync-ffi/tests/api_inventory.txt` and `crates/passwsync-ffi/tests/leakage.rs` are extended by each story's test task.
- Always: test task, see it fail, then implementation. After every Kotlin/XML edit re-run `check_manifest.py android` and `check_sources.py android`.

## Parallel opportunities

- Phase 1: T002 and T004 in parallel.
- Phase 4: the three checker families (manifest/XML/Gradle, sources, bindings) are separate files but share `common.py` and the fixture; write their negative tests in the order given, implement in parallel once T052 is done.
- After Phase 4: Rust test tasks of different stories touch different files (`protections.rs`, `credentials.rs`, `network.rs`, ...) and can be written in parallel, but their implementation tasks all edit `crates/passwsync-ffi/src/api.rs` and run sequentially.
- T037, T036 and T004 run in parallel with T038.

## Implementation strategy

- MVP = Phases 1-4 + Phase 5 (US3) + Phase 6 (US1): host-verified protections, create/unlock/lock. Add US2 for daily use (read, search, copy), then US4/US5 for sync, then US6.
- Extraction first and never relaxed: if a passwsyncd test fails, fix the moved code or the facade, not the test.
- Device-only checks D1-D25 are recorded as pending in quickstart.md (T138); a host-green gate never claims them.
- At each checkpoint run `android/verify.sh --quick` (status 2 by design) and, when tools are available, the full script.
